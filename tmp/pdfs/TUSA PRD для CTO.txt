1. Executive Summary
1.1 Продукт
TUSA.io — это PWA-платформа для дружеских ивентов, объединяющая в одном месте
планирование события, приглашения, RSVP, чат, игры, виртуальные ставки, совместные
покупки, фото-галерею и прогрессию профиля.

1.2 Цель продукта

Собрать в одном продукте все инструменты, которые компания друзей обычно разносит по
разным приложениям:

     создание и координация ивента;
     коммуникация до, во время и после встречи;
     развлечения и игровые механики;
     совместные покупки и сплиты;
     фотоархив и recap;
     социальная прогрессия и retention-механики.

1.3 Целевая аудитория

Основной сегмент: компании друзей 5–20 человек, возраст 17–29 лет.

разрозненных инструментов одним PWA-приложением:

     один event space на всю компанию;

2. Product Vision and Principles
2.1 Видение продукта

Создать основную цифровую операционную систему для дружеских ивентов, которая
работает быстро, предсказуемо, без обязательной установки, с сильным real-time UX и
игровой социальной прогрессией.

2.2 Product Principles

   1. Mobile-first — главный сценарий использования с телефона.
   2. PWA-first — приложение должно работать без app store.
   3. Offline-first — ключевые данные доступны при плохом интернете.
   4. Real-time-first — чат, RSVP, игры и ставки обновляются мгновенно.
   5. Deterministic by design — без ИИ, только объяснимые алгоритмы.
   6. Low-friction onboarding — вход по ссылке/QR, минимум трения.
   7. Social utility before gimmicks — сначала полезность, потом “фишки”.
   8. Host efficiency — сокращение ручной координации организатора.
   9. Privacy by default — закрытые группы, scoped access.
  10. Composable event stack — модули можно включать по необходимости.

2.3 Ограничения продукта
     Без ИИ и генеративных систем.
     Только детерминированные, тестируемые, объяснимые алгоритмы.
     В MVP приоритет — стабильность, скорость, основная полезность.
     Ограничение на сложность медиапайплайна и advanced moderation в MVP.

4. System Architecture (high-level)
4.1 Архитектурный стиль
TUSA.io проектируется как PWA на Next.js 15 (App Router) с real-time слоем на
WebSocket/Socket.io, backend API на Node.js, state/caching через PostgreSQL + Redis +
IndexedDB, media storage на S3-compatible storage (Cloudflare R2).

4.2 Основные слои

       Слой                                 Назначение
Client (PWA)      UI, локальный кеш, offline queue, push, installability
API Layer         REST/GraphQL для CRUD и бизнес-логики
Real-time Gateway WebSocket-сессии, presence, live updates
Workers / Jobs    SMS dispatch, push retries, media processing, recap generation
Database          Source of truth
Cache / PubSub    Быстрый доступ, rate limits, socket fanout coordination
Object Storage    Фото, voice notes, invite audio snippets
CDN / Edge        Быстрая раздача статических и media assets
Observability     Logs, metrics, tracing, alerts

4.3 High-level PWA Architecture
        Next.js 15 App Router для SSR/ISR/RSC, route-level code splitting.
     Service Worker (Workbox):
           precache shell;
           runtime cache API GET;
           background sync для отложенных действий;
           offline fallback page;
           push notifications.
     IndexedDB:
           кеш событий;
           последние сообщения чата;
           queue непросланных сообщений / RSVP / shopping updates.
     Socket.io client:
           real-time transport;
           reconnect with backoff;
           optimistic UI.

4.4 Offline-first подход

Offline-available data

     список ивентов пользователя;
     данные текущего ивента;
     RSVP статусы (last known);
     последние N сообщений чата;
     shopping list текущего ивента;
     игровые состояния в read-only или queued-write режиме;
     профиль, badges, XP snapshot.

Offline-write queue

Локально буферизуются:

     отправка чата;
     реакции;
     RSVP;
     shopping item create/update;
     score updates;
     photo metadata uploads (не сами binary blobs, если сеть отсутствует полностью).

Sync strategy

     client генерирует clientMutationId;
     backend обрабатывает idempotent mutations;
     после reconnect выполняется replay в порядке timestamp + dependency graph.

4.5 Real-time Components

     Компонент          Протокол               Назначение
Chat                    WebSocket Сообщения, реакции, typing, threads
RSVP live updates       WebSocket Обновление attendance
Games                   WebSocket FSM transitions, score sync
Betting                 WebSocket Odds/pool updates
Presence                WebSocket Online state
Broadcast notifications Push/SMS Out-of-band communication

4.6 Edge/cache стратегия

     Static assets: Cloudflare CDN + immutable cache headers.
     Media: CDN with signed access for private event media.
     SSR pages event invite/public landing: edge caching short TTL.
     API GET responses:
           public invite data: 30–60 sec cache;
           event details private: no public cache, Redis-backed.
     ETag / If-None-Match для экономии трафика.
     SW runtime cache policies:
           stale-while-revalidate для non-critical GET;
           network-first для frequently changing event state;
           cache-first для shell/assets.


4.7 Медиа-пайплайн
   1. Client uploads via signed URL.
   2. Object stored in R2/S3.
   3. Worker validates MIME/size/hash.
   4. Optional image compression / thumbnail generation.
   5. EXIF extraction.
   6. Metadata persisted in PostgreSQL.
   7. CDN URL generated.
   8. Gallery real-time refresh event published.

4.8 Deterministic-only approach

     HypeMeter — moving average.
     AutoSchedule — rules based on energy curve.
     Recap Generator — template based.
     Matchmaking — greedy partition.
     Anti-Double — Levenshtein.
     Odds — Elo-lite.
     Photo grouping — EXIF time windows.

5. Functional Requirements

5A. Event Hub Module
5A.1 Цель модуля
Обеспечить полный lifecycle дружеского ивента: создание, приглашения, RSVP,
распределение ролей, оповещения и единая event-space точка входа.

5A.2 User Stories

     Как host, я хочу создать ивент за <2 минут, чтобы быстро собрать друзей.
     Как участник, я хочу ответить “иду/мб/пас” в 1 тап, чтобы не писать в чат.
     Как host, я хочу отправить красивый invite по ссылке/QR, чтобы повысить отклик.
     Как co-host, я хочу видеть статусы и роли, чтобы помогать с организацией.
     Как участник, я хочу получать напоминания даже если push выключен.

5A.3 Основные сущности
     event
     event_participant
     invite
     rsvp_update
     event_role_assignment
     event_blast


5A.4 User Flows

Flow: создание ивента

   1. Пользователь нажимает “Создать ивент”.
   2. Заполняет обязательные поля.
   3. Система валидирует дату, лимит, timezone.
   4. Генерируется event page.
   5. Host получает invite link/QR.
   6. Можно сразу добавить co-host и роли.

Flow: RSVP

   1. Пользователь открывает invite link.
   2. Аутентифицируется или заходит по ограниченному guest flow.
   3. Выбирает статус: going, maybe, pass.
   4. Видит summary и комментарий.
   5. Host получает real-time update.

5A.6 MUST / SHOULD / COULD

MUST

     Создание, редактирование, удаление ивента.
     Invite links и QR.
     RSVP статусы: иду / мб / пас.
     Text Blast через push, SMS fallback.
     Роли: host, co-host, dj, chef, chronicler, treasurer, driver.
     Participant list и live count.
     Event visibility и access control.

SHOULD

     Шаблоны ивентов.
     Duplicate event.
     Reminder schedule presets.
     Invite audio snippet upload до 15 сек.
     Пинованные event notes.

COULD

     Weather/manual checklist blocks.
     Multiple venues/route points.
     Shared countdown widget.

5A.7 Бизнес-правила

     У ивента должен быть минимум 1 host.
     co-host может редактировать ивент, но не может transfer ownership без host action.
     RSVP может изменяться неограниченно до event_locked_at (если задано).
     Invite link может быть single-event scoped.
     QR код декодирует invite URL, а не raw event ID.
     SMS fallback отправляется только участникам с валидным телефоном и opt-in.
     Participant limit: RSVP going не должен превышать лимит, если strict_limit=true.
5A.8 Edge Cases

     Участник ответил RSVP офлайн → должен синхронизироваться без дубликата.
     Срок ивента прошёл, но gallery/chat post-event ещё доступны.
     Host удаляет ивент во время активного чата.
     Invite link утёк вне группы.
     Event time changed after many RSVP confirmations.
     SMS quota exceeded.

5A.9 Acceptance Criteria

     Ивент создаётся за ≤ 5 API round trips.
     RSVP update отображается другим участникам в течение ≤ 1 сек.
     Invite link корректно открывается на mobile web и в установленной PWA.
     QR invite сканируется внешними QR apps и ведёт на HTTPS URL.
     Text Blast делает push first, SMS fallback only for undelivered/inactive push-eligible users
     by policy.
     Ролевые permissions проверяются на backend.


5B. Chat Module
5B.1 Цель модуля

Предоставить real-time коммуникационный слой внутри ивента без необходимости
переходить в внешний мессенджер.

5B.2 User Stories

     Как участник, я хочу писать сообщения в общий чат и подгруппы.
     Как host, я хочу быстро донести update до всех.
     Как участник, я хочу отправить voice note, если неудобно печатать.
     Как пользователь с плохим интернетом, я хочу видеть последние сообщения офлайн.

5B.3 Основные сущности

     chat_thread
     chat_message
     reaction
     voice_note
     message_receipt

5B.4 User Flows

Flow: отправка сообщения

   1. Пользователь печатает сообщение.
   2. Client assigns temp ID.
   3. Message locally stored in IndexedDB.
   4. Отправка по WebSocket.
   5. Server validates membership/thread permissions.
   6. Server ack с canonical message ID.
   7. UI заменяет temp record.

Flow: voice note

   1. Пользователь удерживает кнопку записи.
   2. Записывается до 60 сек.
   3. Blob загружается по signed URL.
   4. Создаётся message типа voice.
   5. TTL задаётся на автоудаление.

5B.5 MUST / SHOULD / COULD

MUST

     Real-time messaging по WebSocket.
     Общий thread на ивент.
     Подгруппы/треды.
     Emoji reactions.
     Voice messages с автоудалением 60 сек.
     IndexedDB local cache.
     Message delivery ack.

SHOULD

     Typing indicators.
     Read markers на уровне thread.
     Message pinning для host/co-host.
     Link previews по allowlist.

COULD

     Mentions.
     Poll messages.
     Quick-reply templates.

5B.6 Бизнес-правила

     Только участники ивента могут писать в event chat.
     Archived/removed participant не может отправлять новые сообщения.
     Voice note hard limit: 60 секунд, max file size configurable.
     Тред может быть public_event, role_scoped, manual_group.
     Реакция пользователя на сообщение по одному emoji может быть только одна.

5B.7 Edge Cases

     Duplicate send on reconnect.
     Message ordering при network jitter.
     Удалённый пользователь остаётся в локальном кеше.
     Voice upload succeeds, message create fails.
     Thread deleted while user typing.

5B.8 Acceptance Criteria

     Средняя latency message-to-fanout < 50 мс внутри региона.
     После reload последние 100 сообщений доступны из IndexedDB.
     Повторная отправка одного clientMutationId не создаёт duplicate.
     Voice note удаляется из UI, DB metadata и object storage по TTL policy.
     Reactions синхронизируются real-time и согласованы между клиентами.

     Только host/co-host/game owner может стартовать.
     Не все игры требуют одинаковый набор игроков.
     Счёт может меняться только в active или paused с host override.
     Leaderboard агрегируется по event и optionally по compashka.

5C.8 Edge Cases
     Игрок покинул игру посреди раунда.
     Нечётное число игроков.
     Одновременные score updates.
     Host disconnect during active game.
     Reconnect with stale state.

5C.9 Acceptance Criteria

     Любая игра описывается FSM-конфигом.
     State transition rules валидируются на сервере.
     Команды формируются детерминированно при одинаковом входе.
     Score history audit trail сохраняется.
     Leaderboard корректно пересчитывается после rollback/override.

9. Algorithms (detailed)
9A. Fair-Shuffle (Fisher–Yates)
Назначение: честное перемешивание списка игроков/челленджей.

Вход: массив A[0..n-1]
Выход: случайно переставленный массив

Шаги

   1. Идти с конца массива к началу.
   2. Для каждого i выбрать j в [0, i].
   3. Поменять A[i] и A[j].

Псевдокод
for i from n-1 downto 1:
    j = randomInt(0, i)
    swap(A[i], A[j])
return A

Сложность: O(n) time, O(1) extra space
Ограничения: нужен качественный PRNG, seedable for reproducibility if required
Edge cases: n=0, n=1, deterministic replay with same seed


9B. Balanced-Teams (greedy partition)
Назначение: приблизительно равные команды по рейтингу/опыту.

Вход: список игроков с весом w
Выход: 2 или N команд

Шаги
   1. Отсортировать игроков по убыванию веса.
   2. По очереди класть игрока в команду с минимальной текущей суммой весов.
   3. Для tie-break — stable deterministic order by user id.

Псевдокод
sort players by weight desc, user_id asc
init teams
for p in players:
    t = team with min(total_weight)
    add p to t
return teams

Сложность: O(n log n)
Ограничения: не оптимально глобально, но быстро
Edge cases: одинаковые веса, нечётное число игроков, принудительные teammates


9C. Round-Robin Pairing
Назначение: генерация расписания пар/матчей.

Вход: список игроков
Выход: список раундов с парами

Шаги

   1. Если нечётное число игроков — добавить BYE.
   2. Зафиксировать первого игрока.
   3. Остальных вращать по кругу.
   4. На каждом раунде формировать пары зеркально.

Псевдокод
if odd(players): add BYE
pivot = players[0]
rest = players[1:]
for round in 1..len(players)-1:
    lineup = [pivot] + rest
    pairs = mirrorPairs(lineup)
    save pairs
    rest = rotate(rest)

Сложность: O(n^2)
Ограничения: подходит для round-robin игр
Edge cases: BYE rounds, player dropout mid-tournament


9D. Elo-lite Rating
Назначение: лёгкий рейтинг для игр и odds.

Вход: ratingA, ratingB, result
Выход: новые рейтинги

Формула

       E(A) = 1 / (1 + 10^((RB - RA)/400))
       RA' = RA + K * (S - E(A))

Где:

       S = 1, если выиграл A
       S = 0.5, если ничья
     S = 0, если проигрыш
     K configurable, напр. 16/24/32

Псевдокод
expectedA = 1 / (1 + 10 ^ ((RB - RA)/400))
newRA = RA + K * (scoreA - expectedA)
newRB = RB + K * ((1-scoreA) - (1-expectedA))

Сложность: O(1)
Ограничения: упрощённая модель; для team games нужен aggregated team rating
Edge cases: новый игрок с default rating, outlier streaks


9E. Anti-Double (Levenshtein)
Назначение: находить вероятные дубли в shopping list.

Вход: новый item name, существующие items
Выход: similarity score / candidate duplicates

Шаги

   1. Normalize string:
           lowercase
           trim
           remove punctuation
           translit simplification
           unit stripping
   2. Посчитать Levenshtein distance до candidate pool.
   3. Преобразовать в similarity.
   4. Если similarity > threshold, показать предупреждение.

Псевдокод
normNew = normalize(name)
for item in items:
    normOld = normalize(item.name)
    d = levenshtein(normNew, normOld)
    sim = 1 - d / max(len(normNew), len(normOld))
    if sim >= threshold:
        candidates.add(item, sim)
return sortBy(sim desc)

Сложность: O(n*m*k) в наивном виде
Ограничения: fuzzy matching несовершенен для разных брендов/языков
Edge cases: "cola", "coca-cola", "кола", "coca cola 2л"


9F. Split Calculator (minimize transactions)
Назначение: минимизировать количество переводов между участниками.

Вход: net balance per user
Выход: список транзакций from -> to -> amount

Шаги

   1. Посчитать баланс каждого: paid - owed.
   2. Разделить на debtors (<0) и creditors (>0).
   3. Жадно матчить крупнейшего debtor с крупнейшим creditor.
   4. Продолжать, пока все балансы не занулятся.

Псевдокод
debtors = sort ascending balances
creditors = sort descending balances
while debtors and creditors:
    d = top debtor
    c = top creditor
    amt = min(abs(d.balance), c.balance)
    add settlement(d -> c, amt)
    update balances
    remove zero balances
return settlements

Сложность: O(n log n)
Ограничения: жадный подход обычно близок к оптимальному
Edge cases: rounding by currency, excluded users, weighted split
